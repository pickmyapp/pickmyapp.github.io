Quick answer

But Starter's 2,500 executions/month dies at a single 15-minute poller (~2,880 runs/month), which is the real reason most teams self-host: unlimited executions for a flat price. The hidden costs are time (2–5 hours setup, 1–3 hours/month maintenance — about $50/month at $25/hr) and the discipline the setup demands: set N8N_ENCRYPTION_KEY before first boot and back it up, use Postgres instead of the default SQLite, and enable execution pruning. If you have no one who enjoys server maintenance, self-hosting is not free — buy the cloud plan.

The execution trap: why this math starts with Cloud's limits

Every "should I self-host n8n" conversation skips to the VPS price, but that's the wrong starting point. The right starting point is the plan you'd be escaping — because n8n Cloud's limits are tighter than the headline numbers suggest.

n8n Cloud Starter is €20/month (annual billing; €24 monthly) for 2,500 executions. An execution is one complete workflow run, however many steps it has. That sounds generous until you do poller math: a workflow that checks for new rows every 5 minutes runs about 8,640 times a month — more than triple the Starter limit — before it does a single useful thing. Even a gentle 15-minute poller burns ~2,880 runs a month, already past Starter's ceiling.

So Starter's real capacity is about three hourly workflows and nothing else. Pro (€50/month annual, 10,000 executions) is the first plan most real setups land on, and Pro 50K (€1,450/year, 50,000 executions) is where growing teams end up. Self-hosted Community Edition gives you unlimited executions for $0 in license fees — and that's the number that makes the VPS math worth doing.

If you haven't worked through the Cloud tiers, our n8n pricing guide breaks down every plan — this article picks up where it leaves off, with the bill you pay instead.

n8n Community Edition costs €0: unlimited executions, unlimited workflows, no per-run fees for permitted internal use (the license is Sustainable Use — fair-code, not open-source; check the terms if you plan to offer it as a hosted service to clients). VPS requirements: the spec table

n8n is a Node.js app with a real database behind it. 1 vCPU / 2 GB RAM is fine for testing a couple of workflows; it will wobble the moment you run anything production-shaped. Here's what to buy:

Provider shorthand (prices change; confirm at checkout): Hostinger KVM1 (1 vCPU/4 GB, $6.49 promo / $11.99 renewal) covers light duty; OVHcloud VPS-1 at €4.49/month is one of Europe's cheapest honest prices; Hetzner CPX31 (4 GB, ~$14/month) is the practitioner favorite for price-per-reliability; managed options like Coolify or PikaPods run $4–8/month if you'd rather not touch Docker directly. Any VPS with Docker support works — n8n doesn't care whose kernel it runs on.

One sizing truth from the field: disk, not CPU, is what usually bites. Execution data accumulates silently; without pruning (covered below), a 64 GB disk can fill in months on a busy instance, and a full disk doesn't degrade n8n — it crashes it. Buy a little more disk than the spec sheet says, then prune anyway.

The setup, 2026 edition: three services, not two

If you've self-hosted n8n before, your muscle memory may be stale. Current n8n docs expect a three-service Docker Compose stack: Postgres, n8n itself, and a separate n8n-runner service. Two-container guides from 2024 are outdated — follow the current docs, not a bookmarked tutorial.

The standard shape, at a high level:

  • postgres — the database. Persistent volume, always. Never use an ephemeral container filesystem for the database.
  • n8n — the app, behind a reverse proxy (Nginx, Caddy or Traefik) that terminates TLS with a Let's Encrypt certificate.
  • n8n-runner — the separate task-runner service that current docs expect for code execution.

Setup order that avoids the classic mistakes: provision the VPS and harden SSH first; install Docker; write your Compose file with Postgres + n8n + n8n-runner; set N8N_ENCRYPTION_KEY before the first boot (next section — this one is non-negotiable); put the reverse proxy in front with HTTPS; verify webhooks work over the public URL (many integrations refuse http); then connect one test workflow and one webhook before migrating anything real.

Two deployment rules worth stating plainly. Skip queue mode (Redis workers plus S3 binary storage) unless you're past tens of thousands of executions a month — it's a distributed system you're volunteering to operate, and at small scale it's pure overhead. And do not expose n8n directly on port 5678 to the internet; the reverse proxy with TLS isn't optional hygiene, it's the entire authentication boundary for the editor.

The encryption-key rule: the one mistake you can't undo

This deserves its own section because it's the only part of self-hosting n8n that has no recovery path. n8n encrypts every stored credential (API keys, OAuth tokens, database passwords) with N8N_ENCRYPTION_KEY. If you don't set it explicitly, n8n generates one at first boot and stores it locally. If that key is ever lost — server rebuilt without the .env file, volume deleted, config lost — every saved credential in your instance is permanently unusable. There's no "forgot key" flow. You re-enter everything by hand.

The checklist: generate the key before first boot, put it in your environment file, and store that file in two places that aren't the server (a password manager and an encrypted backup). Back it up the same day you set up — not the day after the migration is done, because that's the day the server dies. Our n8n vs Make comparison covers the platform choice; this rule applies whichever workflow tool you run.

SQLite vs Postgres: yes, it matters

n8n ships with SQLite as the default database, and the default is a trap for production use. SQLite is a single-file database with coarse locking — fine for testing, increasingly flaky under concurrent workflow execution, and a pain to back up live. Production self-hosting means Postgres.

The practical differences: Postgres handles concurrent executions without the locking contention SQLite exhibits under load; it backs up cleanly (pg_dump against the running container, or a volume snapshot); and it's what n8n's own docs assume for anything serious. The three-service Compose stack includes Postgres precisely because the default isn't the recommendation.

Whatever database you use, turn on execution-data pruning (EXECUTIONS_DATA_PRUNE). Every run stores its data by default; on a busy instance that means gigabytes of logs you'll never open. Set a retention policy (e.g. keep 30 days, prune the rest on a schedule) and your disk stops being a countdown timer.

The real cost: your time, and the honest crossover

Here's the part self-hosting guides bury: the VPS bill is the small money. The honest accounting is:

  • Initial setup: 2–5 hours for someone comfortable with Docker — longer if you're learning the reverse proxy and TLS pieces as you go.
  • Ongoing: 1–3 hours a month — n8n updates (which occasionally need attention, especially major versions), OS patches, backup verification, the odd "why is the disk full" investigation.

At a fully-loaded cost of $25/hour, 2 hours a month of maintenance is $50/month — roughly n8n Cloud Pro. At $40/hour it's $80. That doesn't make self-hosting a bad deal — unlimited executions is worth real money once you're past Pro's 10,000 — but it means "self-hosting is free" is only true if your time is. If nobody on the team enjoys server maintenance, the VPS isn't the cost. The on-call is.

The decision rule: self-host if executions are your constraint (pollers, webhooks, AI loops — the workloads Cloud plans meter hardest) and someone owns the server. Buy Cloud if reliability is your constraint — n8n's Frankfurt-hosted Cloud with their ops team is cheaper than your 2 a.m. debugging session. Migration between the two is straightforward, so this isn't a permanent decision; start Cloud, self-host when the execution bill hurts, and our open-source automation comparison covers the free-tier alternatives if neither fits.

Verdict: the two-year math

Two years of self-hosting: ~$200–$250 in hard costs (VPS at renewal rates, domain, backups) plus roughly 30–60 hours of your time. Two years of n8n Cloud Starter: €480 — for a plan whose 2,500 executions a single 15-minute poller exceeds. Two years of Pro, the plan most real setups need: €1,200.

Self-hosting wins the money math for any team whose automation actually runs. It wins on freedom too — unlimited executions change what you dare to automate. It loses on exactly one axis: someone has to care about the server. If that's you, a $6 VPS and an afternoon is one of the best deals in automation. If it isn't, Pro at €50/month is the honest price of never thinking about it.

Frequently asked questions

How much does it really cost to self-host n8n?

About $6–15/month for a baseline VPS (2 vCPU, 4 GB RAM, 64 GB SSD) plus $10–15/year for a domain and ~$2/month for backups — roughly $91–$108/year in hard costs after promo pricing ends. The software itself (Community Edition) is free with unlimited executions. The bigger cost is time: 2–5 hours to set up and 1–3 hours/month of maintenance, which at $25/hour is ~$50/month — about the price of n8n Cloud Pro.

What VPS specs do I need for n8n?

For light use (a handful of workflows, some webhooks): 2 vCPU, 4 GB RAM, 64 GB SSD. For moderate use (dozens of workflows, AI nodes, daily batch jobs): 2–4 vCPU and 8 GB RAM. Heavy AI or high-volume workloads want 4+ vCPU and 8–16 GB. 1 vCPU / 2 GB is testing-only. Disk matters more than most guides admit — execution data fills disks silently, so buy a little extra and enable pruning.

Is self-hosted n8n really free?

The Community Edition license is free with unlimited executions, but 'free' stops there: VPS (~$6–15/mo), domain, backups, and your maintenance time. The two-year hard-cost total is ~$200–$250 vs €480 for n8n Cloud Starter (a plan most real setups outgrow). It's genuinely cheaper — just not free.

What happens if I lose my n8n encryption key?

Every stored credential becomes permanently unusable. n8n encrypts all credentials with N8N_ENCRYPTION_KEY; lose the key and there's no recovery flow — you re-enter every API key, token and password by hand. Set the key before first boot and store the environment file in two places that aren't the server, the same day you set up.

Should I use SQLite or Postgres with self-hosted n8n?

Postgres for anything production-shaped. SQLite is n8n's default and fine for testing, but its coarse locking gets flaky under concurrent workflow execution and it's awkward to back up live. The current three-service Docker Compose setup (postgres + n8n + n8n-runner) exists because Postgres is the real recommendation — plus enable EXECUTIONS_DATA_PRUNE so execution logs don't fill your disk.

Conclusion

Self-hosting n8n is one of the best flat-price deals in automation — $6–15/month for unlimited executions against Cloud plans that meter every run. The price is honest if you respect it: a proper VPS (not the testing-tier), Postgres with pruning, TLS via a reverse proxy, and the encryption key backed up on day one. Do that and the only recurring bill is a couple of maintenance hours a month. Skip the discipline and the 'free' server becomes the most expensive option — the one that eats a Saturday.
