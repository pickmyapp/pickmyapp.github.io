How to migrate from Zapier to Make without breaking zaps

  • AI Automation Tools
  • Published Oct 26, 2026
  • Updated: October 2026
  • 11 min read
  • By PickMyApp Research Team
Quick answer

There is no one-click Zapier-to-Make importer, so a safe migration is a rebuild: inventory every Zap, rebuild each one as a Make scenario, run both systems in parallel for a full business cycle, and cut over one workflow at a time, lowest risk first. The traps that break migrations are polling triggers (a 1-minute poller burns about 43,200 Make credits a month), filters that cost a credit each on Make but were free on Zapier, and code steps billed at 2 credits per second. Keep paused Zaps for 30 days after cutover as a one-click rollback.

Migrating from Zapier to Make without breaking your automations is a rebuild, not a transfer: there is no one-click importer between the two, and the tools count usage, trigger events, and handle errors differently. Done carefully — inventory first, rebuild in parallel, test everything, then cut over one workflow at a time — you can move without losing a single order, lead, or notification. This guide gives you the full migration playbook, including the billing and trigger traps that break most migrations.

Before you start: inventory everything

The migration starts in Zapier, not in Make. Export or list every Zap with its trigger app, trigger event, each step, any filters, paths, formatters, delays, and the accounts it uses. For each Zap, record three numbers: how often it runs, how many tasks it uses a month, and what breaks if it stops for an hour. That third number sets your cutover order — migrate the lowest-risk Zaps first and the revenue-critical ones last, when your process is proven.

While you inventory, flag the Zaps that will need redesign rather than translation. Multi-step Zaps with Paths become Make scenarios with Routers. Formatter steps become Make's built-in text, date, and number functions or the Tools modules. Delays become Sleep modules. Code steps become the Make Code app — but remember it bills 2 credits per second, so a heavy code step that was free on Zapier now has a meter running. Zaps that use apps Make does not support (Make lists around 3,000 apps against Zapier's 9,000-plus) need a workaround: a webhook, a generic HTTP module, or keeping that one Zap on Zapier while everything else moves.

Also note Zapier's billing unit before you compare prices: Zapier charges per successful action step, with triggers and filters free. Make charges per module execution, including filters. A Zap that costs 3 tasks on Zapier can easily cost 5–7 credits on Make once filters and routers are counted. Price the migration on Make's counting rules, not Zapier's, or the savings you projected will evaporate in the first invoice.

The trigger trap: polling vs webhooks

The single most common migration failure is rebuilding a polling trigger at the wrong interval. Zapier's polling triggers check for new data on a schedule Zapier manages, and many Zapier triggers are instant webhooks under the hood. In Make, you choose: a polling trigger that checks on an interval you set, or a webhook trigger that fires on a real event. The cost difference is enormous — a 1-minute polling trigger burns roughly 43,200 credits a month before any real work happens, while a webhook trigger costs 1 credit per real event and nothing for idle waiting.

For every Zap you migrate, ask whether the trigger app offers a webhook or instant trigger in Make. If it does, use it. If it only offers polling, set the interval to the slowest your business can tolerate: a 15-minute poller burns about 2,880 checks a month, a 5-minute poller about 8,640, and a 1-minute poller the full 43,200. Never copy Zapier's default pace blindly — Zapier's polling cost was hidden inside your task count, and Make's is itemized.

There is a second trigger trap: missed events during cutover. If you switch a Zap off before its Make replacement is live, events in the gap are lost unless the trigger app queues them. Plan cutover so the Make scenario is running and verified before the Zap is paused, and keep both running in parallel for the testing period described below.

Rebuild in Make, step by step

Rebuild each Zap as a new scenario; do not try to automate the translation. There is no official Zapier-to-Make importer, and community converters handle only the simplest linear Zaps. Rebuilding by hand is slower, but it is also the step where you find the dead filters, the unused steps, and the Zaps nobody remembers why they exist — most teams discover 10–20% of their Zaps can simply be deleted.

  1. Start from a template where one exists. Make's template library covers common flows (CRM to email, form to spreadsheet, order to notification). A template is a starting point, not a finished scenario — check every module's mapping before you trust it.
  2. Map fields explicitly. Make shows you the actual output bundle of each module, so run the trigger module once with real data and map fields from the real output, not from memory. Most field-mapping bugs come from assuming a field name that the app does not actually return.
  3. Rebuild filters as Make filters, and count them. Every filter is a credit. Where a Zap had three filters in a row, consider whether one combined condition does the same job.
  4. Rebuild Paths as Routers. Test every route, including the fallback route. A route that never fires in testing will fire in production, usually at the worst moment.
  5. Replace Formatter steps with native functions first. Make's built-in text, date, array, and math functions cover most Formatter uses without extra modules. Reach for the Code app only when a function genuinely cannot do the job, and watch its 2-credits-per-second meter.
  6. Set error handling on every scenario. Make lets you add error-handler routes (ignore, resume, rollback, commit) to modules that can fail. Zapier's default error behavior is different, so do not assume parity — decide, per module, what a failure should do.
  7. Connect accounts fresh. Re-authorize each app connection in Make rather than reusing credentials informally. Note which connections are OAuth (they expire and need re-authorization) and who on the team owns each one.

Test in parallel — never cut over blind

Run the Make scenario alongside the original Zap for at least a full business cycle before switching. For a daily workflow, that means a week; for a weekly report, a full cycle; for a monthly invoice flow, a full month if you can afford the patience. During parallel running, compare outputs, not just "did it run": the same input should produce the same record, the same email, the same spreadsheet row, in both systems.

Build a simple reconciliation check for each migrated flow: a count of inputs, a count of outputs, and a spot-check of field values. Where outputs differ, the difference is almost always a mapping assumption, a timezone setting, or a filter condition — fix it in Make, not by editing data after the fact. Keep a migration log with the date each Zap was rebuilt, tested, and cut over, and who approved it. When something breaks three months later, that log is what lets you find the cause in minutes instead of hours.

Watch your Make credit usage during parallel running: you are temporarily paying for both systems. Make's free tier (1,000 credits a month, 2 active scenarios) is enough for testing one or two small flows, but a real migration needs a paid tier — Core at $9 a month annual gives 10,000 credits, which covers a serious testing phase for most small teams.

Cutover, one workflow at a time

Cut over in ascending order of risk, and never migrate everything on the same day. A workable order is: internal notifications first, then lead capture, then order processing, then billing and payments last. For each cutover: pause the Zap (do not delete it), confirm the Make scenario is processing live events, watch the first few live runs end to end, then — only after a clean period — delete or archive the Zap. Keep paused Zaps for at least 30 days after cutover; restoring a paused Zap is a one-click rollback, while rebuilding a deleted one is a day's work.

Time cutovers away from peaks: not on a Monday morning, not during a sale, not before a holiday. Tell the team which workflows moved and when, and who to call if something looks wrong. The most common post-cutover complaints — "I didn't get the notification" or "the spreadsheet looks different" — are usually a filter or a field mapping, and they are fixable in minutes if you know which scenario to open.

Pitfalls that break migrations

  • Polling intervals copied blindly. A 1-minute poller that was invisible on Zapier costs 43,200 Make credits a month. Use webhooks or slow the interval.
  • Filters counted as free. On Make, every filter costs a credit. A Zap with heavy filtering gets more expensive, not cheaper, after migration.
  • Code steps metered. The Make Code app bills 2 credits per second. A slow code step can dominate a scenario's cost.
  • Apps Make does not support. Check every trigger and action app before you start. For unsupported apps, use a webhook or HTTP module, or leave that Zap on Zapier.
  • Timezone and date-format differences. Make and Zapier format dates differently in some apps. Test date fields explicitly, especially for scheduling and invoicing flows.
  • Error handling assumed, not set. Zapier and Make fail differently. Set an error route on every module that touches money, customers, or external systems.
  • Deleting Zaps too early. Keep paused Zaps for 30 days as rollback. Deletion is permanent and unrecoverable.
  • No owner for connections. OAuth connections expire. Assign every app connection to a named person, or the scenario will silently stop one day.

What you actually save

Most small teams save money, but the size of the saving depends on how Zapier counted their usage. Zapier's Professional plan starts at $19.99 a month annual for 750 tasks and scales steeply — 5,000 tasks at $89, 10,000 at $129, 20,000 at $189. Make's Core plan starts at $9 a month annual for 10,000 credits. A team using 5,000 Zapier tasks a month might pay $89 on Zapier and $9–16 on Make for the same volume, if their credit count stays honest. But a team whose Zaps rely on heavy filtering, polling, or code steps can find Make's credit count higher than expected — which is why the inventory and parallel-testing steps above are not optional. The saving is real, but only for teams that count honestly before they commit.

Frequently asked questions

Is there a one-click way to import Zaps into Make?

No. There is no official Zapier-to-Make importer. You rebuild each Zap as a Make scenario by hand, or start from one of Make's templates for common flows. Rebuilding is slower, but it is also how you find dead Zaps, redundant steps, and filters that no longer make sense.

Will my Zaps stop working during migration?

Not if you run both systems in parallel. Build and test the Make scenario while the Zap keeps running, compare outputs for at least a full business cycle, then pause the Zap and let Make take over. Keep paused Zaps for 30 days as a one-click rollback before deleting them.

Why does Make cost more than I expected after migrating?

Usually polling, filters, or code steps. Make charges a credit per module execution including filters, while Zapier's filters were free; a 1-minute polling trigger burns about 43,200 credits a month; and the Code app bills 2 credits per second. Switch polling triggers to webhooks, combine filters, and audit code steps first.

What if Make does not support one of my apps?

Make supports around 3,000 apps against Zapier's 9,000-plus, so gaps happen. Workarounds are a webhook trigger, a generic HTTP module calling the app's API, or leaving that single Zap on Zapier while everything else moves. Check every app before you start migrating, not after.

How long does a Zapier to Make migration take?

For a small team with 10–20 Zaps, plan one to two weeks: a day for inventory, a few days for rebuilding, at least a full business cycle of parallel testing, and a day per risk tier for cutover. Larger Zap libraries scale roughly linearly — the testing phase, not the rebuilding, is what takes the time, and it is the phase you should not skip.

Conclusion

Migrating from Zapier to Make without breaking anything comes down to discipline, not tools: inventory first, rebuild by hand, count credits honestly, test in parallel for a full cycle, and cut over one workflow at a time, lowest risk first. The savings are real — Make's pricing undercuts Zapier substantially at most small-team volumes — but only for teams that respect the counting differences, especially polling triggers and filters. Do the inventory this week, migrate the safest workflow first, and let a clean parallel run earn your confidence before you touch the workflows that move money.
