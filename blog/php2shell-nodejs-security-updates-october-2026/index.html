PHP2Shell and the Node.js October 2026 security updates explained: what website owners must check today (2026)

  • Web Hosting
  • Published Oct 22, 2026
  • Updated: October 2026
  • 14 min read
  • By PickMyApp Research Team
Quick answer

On October 21, 2026, the PHP Foundation patched PHP2Shell — two critical remote-code-execution flaws (CVE-2026-109618 and CVE-2026-109619, both CVSS 9.2) in the PHP runtime itself, exploitable by an unauthenticated HTTP request with no login. The fixed builds are PHP 8.5.12, 8.4.27, 8.3.36 and 8.2.35; PHP 7.4–8.1 and older get no official release. The same day, Node.js shipped security releases (22.23.4, 24.22.1, 26.12.1) fixing 10 vulnerabilities, including a High-severity Brotli RCE. If your site runs PHP, check your version today — in cPanel under “Select PHP Version” or in WordPress under Tools → Site Health → Info → Server. Updating WordPress core, plugins or themes will not fix PHP2Shell; only the PHP runtime update does.

What PHP2Shell is — and why it's not a WordPress problem

Most website security scares are plugin problems: a vulnerable contact form, a sloppy theme, a page-builder with a hole. PHP2Shell is different. It lives in the PHP runtime itself — the engine that executes your site's code before WordPress, Joomla, Drupal or your custom app even starts. Two critical remote-code-execution (RCE) vulnerabilities, disclosed by the PHP Foundation on October 21, 2026, let an attacker run arbitrary code on the server with no login and no credentials — just a crafted HTTP request to a PHP endpoint.

PHP's own advisory demonstrates an unauthenticated exploit against Apache mod_php in a default configuration that fires before any application code runs — meaning your WordPress security plugin never gets a chance to intervene. All PHP web setups are in scope: mod_php (which PHP rates the highest risk), PHP-FPM, php-cgi, FrankenPHP and LiteSpeed.

The scale of exposure is what makes this a check-today story rather than a read-later one. PHP runs on 69.3% of websites with a known server-side language (W3Techs, cited by CriticalStart on October 21). Exposure estimates put roughly 1.3–5.1 million internet-exposed PHP hosts in reach, and BlackKite's scanning found about 1.9 million internet-facing PHP hosts — of which 72.5% of those disclosing a version run end-of-life branches that will never receive an official fix.

The two flaws: CVE-2026-109618 and CVE-2026-109619

“PHP2Shell” is the researchers' name for the pair. Both score CVSS v4.0 9.2 — firmly in critical territory — and both are memory-safety flaws in how PHP handles requests:

PHP2Shell: the two CVEs at a glance
CVEWhat it isHow it's reached
CVE-2026-109618RCE via out-of-memory corruption: OOM handling can interrupt PHP while internal request data is only partially initialized, and request cleanup then treats the invalid data as validMultipart (file upload) request parsing
CVE-2026-109619RCE via stale global state: request-owned internal state survives after its backing memory is freed, and a later request on the same worker reuses that stale stateA later request on the same worker process

Validated RCE setups: mod_php for CVE-2026-109618; mod_php and PHP-FPM for CVE-2026-109619. Two things matter for non-engineers. First, there is no configuration workaround — PHP's own developers state that patching is the only complete fix and no configuration closes either hole. Second, the flaws were reported back in August 2026, and the researchers credit frontier AI models with compressing an exceptionally complex exploit chain into roughly one week of work — a reminder that the window between disclosure and weaponization keeps shrinking.

Which PHP versions are fixed — and which get no patch at all

The PHP Foundation shipped patched builds on October 21, 2026, about 25 minutes ahead of its announced 14:00 UTC target. If your server runs one of these, you're covered once updated:

  • PHP 8.5.12 (current branch)
  • PHP 8.4.27
  • PHP 8.3.36
  • PHP 8.2.35

Everything older is bad news. PHP 8.1 and older received no official release — the PHP security team published only minimal source-only backports for 7.4, 8.0 and 8.1, which most shared hosts will never apply. There is no official fix for 7.3 and earlier or 5.x. Given BlackKite's finding that nearly three-quarters of version-disclosing PHP hosts run end-of-life branches, a huge share of the internet's PHP footprint is sitting on versions that can never be patched in place — those sites need to upgrade, not just update.

If your host still runs you on 7.4, 8.0 or 8.1, treat this as the forcing event to plan the upgrade you kept postponing. Those branches were already past end-of-life before PHP2Shell; now they're past it and exposed to a critical unauthenticated RCE.

Disclosure timeline — and the contested exploitation picture

The timeline moved fast, and the exploitation picture as of October 22 is genuinely contested — worth stating carefully rather than picking the scariest headline:

  • August 2026: researchers report the flaws to PHP. The PHP Foundation credited Calif (Calif.io), OpenAI and Wiz for research and responsible disclosure.
  • October 20, 2026 (morning): a now-removed Hacker News post leaks the two reserved CVE IDs; watchTowr confirms and reproduces CVE-2026-109618. The PHP Foundation issues an advance notice of an emergency release, moved up a day from the originally planned October 22 disclosure. CERT-EU issues advisory 2026-018.
  • October 21, ~03:02 UTC: Cloudflare activates default WAF rules for free and paid plans. Cloudflare's CTO reported early attack traffic at 07:43 UTC — before the patches shipped.
  • October 21, ~13:35 UTC: patches ship. Researcher writeups and a demonstration video appear; proof-of-concept code surfaces on GitHub. watchTowr reports exploitation observed in its global honeypot network from October 21; Aikido reports exploitation in the wild.

On the other side: the PHP Foundation said the PoCs circulating after the leak that it inspected were not functional exploits at release time; CISA said it had not observed exploitation at advisory publication; Germany's BSI, Huntress (as of Oct 21, 16:30 ET) and Australia's ACSC reported no confirmed exploitation; and PHP2Shell is not in the CISA Known Exploited Vulnerabilities catalog (catalog version 2026-10-21, checked October 22). No confirmed public report of an actual compromise attributed to PHP2Shell had surfaced as of October 22.

The honest read: attack attempts are real and documented, functional exploitation is plausible and expected soon given the public technical details — but confirmed compromises had not been established when this article was written. Patch anyway, and patch today.

The Node.js October 2026 security release: 10 fixes across three lines

Bundled into the same news cycle, Node.js shipped its own security release on October 21, 2026. If you run Node.js apps, servers or APIs (build tools, headless CMS backends, real-time services), this one is yours to act on. If your site is WordPress on shared hosting, Node.js almost certainly doesn't touch your stack — skip to the checklist.

Patched versions: Node.js 26.12.1 (Current), 24.22.1 (LTS, codename Krypton), 22.23.4 (Maintenance LTS, codename Jod). Ten vulnerabilities were fixed — 4 High, 3 Medium, 3 Low by the Node.js project's own severity labels:

The worst is CVE-2026-111497: a Brotli decoder out-of-bounds write that can permit remote code execution from crafted compressed data, on all three lines. Exact exploitation prerequisites aren't public — the advisory confirms impact, not exploitability conditions. The TLS hostname-verification bypasses are the sleeper risk for API-heavy backends: a certificate that shouldn't authenticate an endpoint suddenly can.

Two things bundled into this release deserve attention beyond the CVEs. First, the bundled root certificates were updated to NSS 3.131.1, including removal of trust tied to the eMudhra intermediate CA compromise — eMudhra's intermediate private keys could be reconstructed from public certificates, ~16 certificates were revoked, browsers blocked them October 17–20, and roughly 30,000 certificates need reissuing. If your services pin or depend on affected chains, check them. Second, end-of-life lines get no fixes: Node 18, 20 and 25 are unpatched (Node 20 reached EOL April 30, 2026). Note the transitions: Node 26 becomes LTS on October 28, 2026, and Node 24 moved to maintenance mode on October 20.

Upgrade path: run node -v, move to 22.23.4, 24.22.1 or 26.12.1 for your line, rebuild container images and restart services, then confirm the running binary reports the patched version. Single Executable Applications must be rebuilt against the patched runtime — and note CVE-2026-106074, which means previously-built snapshots may have been generating predictable “random” values.

What website owners must check today: the 7-step list

No theory — here's the actual checklist, in order:

1. Find out which PHP version your site runs

In cPanel, open “Select PHP Version” (or MultiPHP Manager / PHP Selector, depending on your host's skin). In WordPress, go to Tools → Site Health → Info → Server and read the PHP version line. If you can't find it, ask your host's support chat — this is a five-minute question, and right now it's the most important one.

2. Get onto a patched build — or push your host to

The fixed releases are 8.5.12, 8.4.27, 8.3.36 and 8.2.35. On shared hosting, the host controls the PHP binaries — you can't patch the runtime yourself. Your job: verify your site is on a patched version (or on an 8.x branch your host has patched), and open a ticket pushing support if they haven't deployed it yet. If you're still on 7.4, 8.0 or 8.1 — which get no official release, only source-only backports — plan the upgrade now, not next quarter. If you're on 7.3 or older, you're on an unfixable branch: upgrading is the only remediation.

3. Back up before you touch anything

Run a full backup first — cPanel's Backup Wizard, or your backup plugin — before any PHP version switch or update. A PHP minor-version change can break old plugins; you want a rewind button.

4. Understand what does NOT fix PHP2Shell

Updating WordPress core, plugins and themes will not fix PHP2Shell — the fix is at the PHP runtime/infrastructure level, and CMS or plugin updates don't apply it. Do update everything anyway as general hygiene, and after the runtime update, restart PHP processes (e.g. a PHP-FPM restart) so the patched binary is actually what's running.

5. Treat your WAF as a bandage, not a cure

Cloudflare enabled default WAF rules on October 21 and reports blocking attack traffic — genuinely useful as a stopgap. But PHP's own developers are explicit: patching is the only complete fix; no configuration closes either hole. A WAF buys you time; it doesn't close the vulnerability. If you're behind Cloudflare already, you're partially shielded — keep going with steps 1–2.

6. Node.js users: upgrade, rebuild, restart

Only relevant if you run Node.js apps or APIs. Run node -v, upgrade to the patched release for your line (22.23.4 / 24.22.1 / 26.12.1), rebuild your container images, restart the services, and verify the running binary. Single Executable Apps need a rebuild against the patched runtime.

7. If you suspect compromise, rotate secrets

Especially on a server that was unpatched while attack traffic was observed: change admin passwords, reissue API keys, and rotate salts/keys. A patched server with stolen credentials is still a compromised site. Three myths to ignore

“I updated WordPress, so I'm safe.” No — the vulnerability is below WordPress, in the runtime. Application updates are hygiene, not remediation.

“My WAF blocks it, so I can wait.” WAF rules (like Cloudflare's October 21 defaults) blunt attack traffic, but attackers iterate on bypasses. The window between a WAF rule and a bypass is measured in days. Patch.

“My host handles security.” Maybe — but verify. Open the ticket, ask for the patched PHP build by version number, and confirm your site is actually running it. Trust, but verify, especially on budget shared hosting.

Frequently asked questions

What is PHP2Shell?

PHP2Shell is the researchers' name for two critical remote-code-execution vulnerabilities in the PHP runtime itself — CVE-2026-109618 and CVE-2026-109619, both rated CVSS v4.0 9.2. They let an attacker execute code on the server via an unauthenticated HTTP request, before application code like WordPress even runs. The PHP Foundation disclosed and patched them on October 21, 2026.

Which PHP versions fix PHP2Shell?

The patched releases are PHP 8.5.12, 8.4.27, 8.3.36 and 8.2.35, all released October 21, 2026. PHP 8.1 and older received no official release — only minimal source-only backports for 7.4, 8.0 and 8.1 — and there is no official fix for 7.3 and earlier or 5.x. Sites on end-of-life branches must upgrade, not just update.

Does updating WordPress, plugins or themes fix PHP2Shell?

No. PHP2Shell is a vulnerability in the PHP runtime/infrastructure layer, and CMS or plugin updates do not apply the fix — only updating the PHP runtime to a patched build remediates it. Still update WordPress core, plugins and themes as general security hygiene, and restart PHP processes (e.g. PHP-FPM) after the runtime update.

Is PHP2Shell being exploited in the wild?

The picture is contested as of October 22, 2026. Cloudflare reported early attack traffic before the patches shipped, watchTowr observed exploitation in its honeypot network from October 21, and Aikido reported in-the-wild exploitation. But the PHP Foundation said inspected PoCs weren't functional exploits at release time, CISA said it had not observed exploitation, BSI/Huntress/ACSC reported none confirmed, and PHP2Shell is not in CISA's Known Exploited Vulnerabilities catalog. No confirmed public compromise had been attributed to it — but the technical details are public, so treat patching as urgent regardless.

Do I need to worry about the Node.js updates if my site is WordPress on shared hosting?

Almost certainly not — Node.js doesn't run a typical WordPress stack. The October 2026 Node.js security release (22.23.4, 24.22.1, 26.12.1, fixing 10 vulnerabilities including a High-severity Brotli RCE) matters if you run Node.js apps, servers, APIs or build pipelines. If that's you: upgrade, rebuild container images, restart services, and rebuild any Single Executable Apps against the patched runtime.

Conclusion

PHP2Shell is the rare vulnerability that deserves the urgent tone: an unauthenticated RCE in the runtime powering most of the web, with attack traffic already observed and patches available since October 21, 2026. The fix is simple — get on PHP 8.5.12, 8.4.27, 8.3.36 or 8.2.35, or push your host to — and the trap is equally simple: believing a WordPress or plugin update covers you. It doesn't. Check your PHP version today, back up first, update the runtime, and restart PHP. Node.js shops: upgrade to the patched line release, rebuild your images, and move on. The internet's patch window for flaws like this is measured in days, not months.
